* bhw-www

The third iteration of my personal website. It was quite fun building this with
Common Lisp circa 2020-2024. The use of Large Language Models has taken over
post 2025. Pull requests and patches -- see "bhw.asd" for the
correct mailing address -- are most welcome.

** Development Quick Start

Prerequisite(s): [[https://guix.gnu.org/][GNU Guix]], which provides [[http://www.sbcl.org/][SBCL]] and every Common Lisp dependency.
=guix.scm= defines the package, including the dependency Guix lacks
(graph-db) and, grafted, a CFFI without its reference to GCC. Its inputs are
the development environment. Production builds it with the host's own Guix
(see "Deployment").

The code is four parts served by one process, each a group of
package-inferred systems under =src/=:

- =site/= -- the personal website's pages, and the layout every page shares.
- =bible/= -- the Douay-Rheims reader: its graph-db store (=database=), the
  text and its search (=text=), and its pages (=reader=).
- =slack-bot/= -- the van-booking bot: its graph-db store (=database=), the
  language layers (=nlp=, =booking-nlp=), the schedule
  spreadsheet (=van-booking=, with the Apps Script it talks to in
  =van-booking.gs=), and the Slack endpoints and reminders (=bot=).
- =plp/= -- the praise lyrics presenter, at =/plp=: songs and their slides
  (=song=), their graph-db store with tags and setlists (=database=), the
  import of the Companions of the Cross chord book (=import=), the rooms
  that tie an operator's console to its screens (=live=), and the two pages
  (=console=, =screen=). The screen is put full screen on the display the
  congregation sees; the console jumps to a verse, the refrain or the bridge
  at a key press, and as a musician's page shows the whole song with its
  chords over the words, in the key asked for.

=main.lisp= starts them all (=initialize-application=); =store.lisp= is the
graph-db plumbing the databases share. The tests mirror this tree under
=src/tests/= and use [[https://github.com/fukamachi/rove][Rove]].

The pages are built by [[https://github.com/rabbibotton/clog][CLOG]] over its websocket (a browser without
JavaScript sees nothing): a fork of it in =clog/=, its core and CLOG-GUI
served by Hunchentoot alone, without the documentation, database, Clack and
Lack layers or jQuery (=clog/README.org=). None of the pages, the static blog's
included, runs a script of the site's own: what moves on the index page is
CSS, and the colour theme is a cookie that the navbar's toggle sets by
posting to =/theme=. CLOG reads it for its pages; the file server writes it into each
static HTML file it sends, and links =assets/dark.css= when it applies.

1. Clone the repository and enter the development environment,

   #+begin_src bash
   $ git clone https://github.com/bhwdev/bhw-www.git && cd bhw-www
   $ guix shell -D -f guix.scm
   #+end_src

   =guix shell= caches the environment and rebuilds it when =guix.scm=
   changes.

2. Within [[https://www.gnu.org/software/emacs/][Emacs]] started from that shell, start a Common Lisp IDE ([[https://github.com/joaotavora/sly][SLY]]) REPL
   buffer with =M-x sly=. ASDF finds the dependencies through =XDG_CONFIG_DIRS=,
   which the shell sets.

   Claude Code works through [[https://github.com/cl-ai-project/cl-mcp][cl-mcp]], a REPL-backed MCP server, where that
   costs fewer tokens than reading files; =CLAUDE.md= says when and how it is
   set up.

3. Load bhw-www, run its tests & start a local development server.
   Loading opens nothing; =initialize-application= opens the databases. The
   bible pages and search need the bible store and Montezuma index under
   =/var/local/bhw-www/=, which are not in the repository, so the
   bible tests skip without them.

   #+begin_src lisp
     CL-USER> (asdf:test-system "bhw-www")
     ;; Starts web server at http://localhost:8080.
     CL-USER> (bhw/main:initialize-application)
     CL-USER> (bhw/main:terminate-application)
   #+end_src

4. To build the executable, which compiles the system, runs the tests and
   then saves the program from a fresh image that loaded only the system,

   #+begin_src bash
     $ guix build -f guix.scm
     $ /gnu/store/...-bhw-www-2.0.0/bin/bhw-www
   #+end_src

   Prefix =guix time-machine --commit=COMMIT --= to build it with another
   Guix, such as production's (=ssh oci-a1-flex guix describe=).

   Production runs it as a Shepherd service of its own user: Hunchentoot on
   127.0.0.1:8080 and Slynk on 4005, with these in its environment:

   #+begin_src bash
     HOME=/var/lib/bhw-www
     BHW_WWW_DATA=/var/lib/bhw-www/  # the bot's store, graph-db's system directory
     SSL_CERT_DIR=/etc/ssl/certs                     # Guix's OpenSSL looks in its own store directory otherwise
     SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt
     # and SLACK_BOT_TOKEN, SLACK_SIGNING_SECRET, VAN_SCHEDULE_SECRET,
     # BHW_PLP_PASSPHRASE (without it the presenter saves nothing)
   #+end_src

   The presenter's songs are not in this repository. They are staged on a
   development machine from the chord book's PDF
   (=(bhw/plp/import:import-book #p"...pdf")=, which needs poppler's
   =pdftotext=), read and corrected in =<data root>/plp/staging/=, and copied
   to the host with the waiting images (=<data root>/plp/images/=, with a
   =credits.txt= of =file<TAB>credit= lines). The store is not copied: its
   type ids belong to the host's graph-db system directory. On the host,
   through Slynk, =(bhw/plp/import:load-staging)= stores the staged songs, as
   often as they change.

   Songs staged before the import read the chords get them from the PDF with
   =(bhw/plp/import:add-chords-to-staging #p"...pdf")=, which changes nothing
   else in the files. On the host, =(bhw/plp/import:add-chords-to-store)=
   then gives each stored song the chords of its staged lines and keeps what
   was corrected in the store, which =load-staging= would replace.

   The bible store and Montezuma index are in =/var/local/bhw-www/=.

** Deployment

A push to =master= deploys. [[file:.github/workflows/deploy.yml][.github/workflows/deploy.yml]] connects to the
production host with a key that can do nothing there but run its deploy hook,
and hands it the commit: =ssh deploy@HOST COMMIT=. sshd passes =COMMIT= to the
hook in =SSH_ORIGINAL_COMMAND=, and the hook refuses (exit 64) anything but 40
hex digits. It fetches GitHub's archive of that commit, builds =guix.scm= with
the host's Guix (the build runs the test suites; a failure stops the deploy
before the restart), installs the program as the next generation of the
profile =/var/guix/profiles/per-user/deploy/bhw-www=, and restarts the
service. The hook runs as the unprivileged account =deploy=, not root:
evaluating =guix.scm= runs this repository's code, and sudo allows =deploy=
only the two =herd= commands that enable and restart the service. The host
runs Guix System; the hook, the service and Caddy are its system
configuration, kept outside this repository. So the host's Guix, not this
repository, fixes the SBCL and Lisp libraries that production builds with.
To roll back, as =deploy= (=sudo -u deploy= from root): =guix package
-p /var/guix/profiles/per-user/deploy/bhw-www --roll-back=, then, as
root, =herd restart bhw-www=. One-time setup:

1. On the host, allow a new deploy key in the =deploy= account's authorized
   keys, for the hook only:

   #+begin_src text
     restrict,command="/gnu/store/...-bhw-www-deploy" ssh-ed25519 AAAA... bhw-www-deploy
   #+end_src

2. In the repository's settings on GitHub, create the environment =production=,
   limited to the =master= branch, with the secret =DEPLOY_SSH_KEY= (the private
   key) and the variables =DEPLOY_HOST= (the host's address) and =DEPLOY_KNOWN_HOSTS=
   (=ssh-keyscan= output for it).

The Slack bot reads and writes the van schedule through a Google Apps Script
web app, =src/slack-bot/van-booking.gs=, which is deployed by hand: its header
says how. Deploy a change to it before the Lisp that relies on it.

online documentation.
